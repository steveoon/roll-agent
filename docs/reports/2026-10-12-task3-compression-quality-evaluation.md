# Task 3 压缩效果与信息保留评估

用户本轮澄清：先评估当前 Task 3，再据结果决定优化；“40–50%”指压缩后仍占整个窗口的 40–50%。本轮没有实现 Task 4、Phase 2 或修改压缩生产代码。

## 结论

1. **已复现压缩后仍占窗口 41.60% 的路径。** 50 万窗口下，完整准备请求估计从 410,516 降到 208,024；一批处理后低于 75% 软目标，维护正常结束。这说明该现象可以由当前停止策略与分批吞吐共同产生，不是“模型最多只能压到一半”的证明。也不能凭合成样例断言用户历史会话的精确因果。
2. **Task 3 没有压缩到某个较低占用率的目标。** 触发线与恢复目标目前共用 75%。相近总量分散在更多消息中时，单批覆盖的比例更小；同样约 42 万的请求，100 轮样例压缩后还占 72.22%。加入旧工具账本后，公平选取修复饥饿，但每批处理的消息更少，本例停在 67.20%。
3. **发现确定性的信息保留缺口，真实任务质量不能判为通过。** 单条模型证据摘录只保留前 256 字符；删除前缀的另一路上下文又受约 64 Ki 字符输入预算限制、超限保留头尾。部分中后部事实既不进入摘要输入，也不进入压缩后的请求。来源校验随后用引文派生的文本替换模型候选概括，这限制了提取消息后部事实的能力。原始记录仍持久保存，检索可补充，但是否主动检索需要真实模型评估。
4. **这项语义保留限制在 Task 3 前已存在。** 对已接受 Task 2 的语义模块快照执行同一探针，结果相同。不能称为 Task 3 引入的回归。
5. **尚无真实模型的任务完成率、压缩耗时或有效工具步数结论。** ChatGPT 启动认证独立调查复现了 TLS 前断连/连接超时，真实账号续期和推理仍未恢复验证。本轮没有替换模型、改认证或用 mock 结果冒充真实编码表现。

## 方法与范围

可复现脚本：`scripts/bench/compaction-retention.mjs`。

- 使用当前 `AgentSession`、生产 SDK preparation/guard、结构化摘要校验、Store CAS、SQLite 重开及 transcript 工具接线。
- 生成长编码检查记录的合成历史，在早部、消息中部和尾部嵌入三个精确事实标记。没有读取用户聊天正文作为测试输入。
- 摘要模型是确定性 mock：保留可见事实引用，其他合成填充作为已审阅材料；推理模型仅返回固定完成文本。**这不是语言模型质量评测，也不计为完成编码任务。**
- 预算为同一 `estimatePreparedRequest` 口径的完整请求估计；无真实 tokenizer/Provider usage。mock usage 与估计一致，没有用人为负残差降低预算。
- 工具混合样例加入 40 条合成成功工具账本记录以隔离证据队列竞争；没有执行 40 次真实工具。
- 原始材料和关键事实在 SQLite 关闭重开后再次核对。探针临时数据库完成后清理；未写用户现场线程数据库。

## 信息保留

在 30/40 轮纯消息样例中：

| 事实位置 | 原始记录 | 摘要模型实际输入 | 压缩后下一次请求 | SQLite 重开后原始 transcript |
| --- | --- | --- | --- | --- |
| 早部、消息开头 | 有 | 有 | 有 | 有 |
| 较早消息中部（约第 5000 字符） | 有 | 无 | 无 | 有 |
| 较早长消息尾部 | 有 | 无 | 无 | 有 |

这说明“coverage 前进且无错误”不能作为信息完整保留的验收条件。这里的 1/3 是三个特意放置的探针标记结果，不能推广成真实任务 33% 保留率或成功率。100 轮和混合材料的可见性不同，完整逐项结果保存在 JSON。

另一个不依赖摘要模型能力的探针：原文后部包含关键数值，给校验器一个包含正确数值的候选 `text`，同时引用实际展示的前 256 字符。校验结果把 text 改为引文内容，关键数值不在最终语义状态，证据仍被记为 covered，没有 rejection。它展示的是当前“只允许有界引文作为事实文本”的设计取舍，不是证明校验器能接受任意伪造事实。

源码依据：

- `compaction-semantic-state.ts:643`：`modelFacingEvidenceSummary` 截到 256 字符。
- `compaction-semantic-state.ts:1072`：`acceptedText` 来自 `authoritativeTextFromQuotes`，不是候选 text。
- `compactor.ts`：`buildCompactionDraftPrompt` 受 `64 * 1024` 字符预算限制，`truncatePrefixForPrompt` 保留头尾。
- `compaction-checkpoint.ts:475`：语义 reminder 另有 8,000 字符上限；大状态只能部分进入下一次请求。该上限是额外保留边界，本轮未将其单独归因成探针事实丢失的原因。

Task 2 基线语义模块 SHA-256：`32b2f0a16c7b6d75b56b57ef5923b18b84482ebc29e772aebdfa9ce141059fbc`，与原基线 manifest 一致。其相同探针亦为 `acceptedStateContainsFact=false, covered=true, rejections=[]`。

## 后续优化判断

建议先改善重要事实的提取与保留，再比较更低的恢复目标；仅增加删除量可能扩大上述信息缺口。

1. **事实提取与来源定位分开设计。** 对长消息/工具结果采用可定位片段或分页提取，使消息后部也有处理机会；允许经过验证的紧凑事实表示，保留原文位置与必要引文。不能简单放开任意模型概括或把引文校验删掉。
2. **区分触发阈值与恢复目标。** 用相同任务比较多个恢复目标，联合观察事实保留、总结调用成本、净释放和下一次维护前有效工具步数。20%/35%/50% 可作为实验组而非直接落地的默认值；保持硬预算检查和原回合限制。
3. **认证恢复后再做真实编码 A/B。** 固定同一模型和设置，对完整历史、当前 Task 3 压缩历史和候选改进分别运行相同隔离任务；关键约束分布在早期、消息中段与尾部，以独立测试检查正确性、约束遵守、重复副作用、是否主动回查及工作量。每组至少重复三次，报告实际 usage/耗时，不以模型“已完成”的回复判成功。

Task 4 原计划主要提供持久化诊断和集成验收，能帮助收集以上数据，本身不改变摘要密度和恢复目标。本轮按用户澄清保持其未实施。
