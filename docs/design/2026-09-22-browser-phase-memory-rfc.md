# 浏览器任务阶段记忆：设计草案

状态：用户已批准先实施A；A实现与调用边界见 ../reference-browser-phase-memory.md。B/C仍为设计草案。范围：browser_operate 一次任务中的进度、证据、剩余义务与完成判定。首页输入预算、导航能力和浏览器新标签页接管另立工作项。

## 1. 要解决的具体问题

在“打开目标预览 → 读取资料 → 关闭并返回列表”中，起点和终点可以是同一张列表。只有当前快照不能区分二者；点击日志也不能证明读到了正确对象的完整资料。

已核对当前代码：

- runBrowserTask 每次调用新建 steps、resolvedValues、pickerMemory、visits 和 guidance。
- taskState 传入最近16条动作，包含操作、显示名称、执行标记和错误，但没有与目标对象绑定的历史读取证据。
- resolvedValues 记录输入/选项选择，不是读取结果集；77.1秒往返案例的三次调用均为空。
- finalObservation 主要描述最后页面；关闭预览后，正文没有作为持久读取证据保留在任务状态中。
- completion 与 operation 在同一请求独立作答，现有路由仅在operation=DONE时消费completion；不能期待动作题读取另一个问题的新答案。

因此，确定存在的是“没有显式的读取进度及证据模型”；不能仅凭重复打开行为断言所有错误都由缺少历史造成。原始provider日志没有保存每一轮完整HTTP请求体，逐轮输入只能结合源码与保留快照分析；不得把重建输入当作原始请求。

参考对话：ChatGPT「修复浏览搜索缺口」，conversationId 6ab1ebb2-ab98-83ec-913b-7c5c2c80e087。采用其中的历史/当前状态区分、证据保留和fan-out依赖约束。官方TypeSafe文档本轮无法访问，以下接口接线以本地源码和已读取skill为依据，性能上限不作官方保证。

## 2. 推荐方案

为执行循环增加一个任务内进度对象和一份不可变证据集合。外层Roll开始时声明任务义务；Jev选择语义对应的证据和动作；代码校验引用、保存原文、推进阶段。最后统一把历史读取证据与最新页面交给Roll验收、汇报。

第一版聚焦“单个目标对象，取得若干资料，再到指定终点”的任务。用通用语义字段表达，不包含网站名称、CSS路径、坐标或固定菜单步骤。普通表单可继续现有路径，不强迫所有字段变成独立阶段。

阶段记忆属于短期工作状态。第一版不引入向量检索、长期记忆库、自由文本滚动摘要或可编程工作流引擎。

## 3. 三类数据必须分开

| 数据 | 谁创建/更新 | 意义与约束 |
|---|---|---|
| TaskContract 任务约定 | Roll在开始时准备一次；代码校验结构 | 原始目标、目标描述、需要取得的资料、必须发生的历史步骤、最终页面条件；不含操作路径 |
| EvidenceStore 证据集合 | 观察器提供候选，Jev选择，代码保存 | 原文、来源、读取时刻、对象绑定及选取依据；关闭页面后仍可引用 |
| TaskProgress 任务进度 | 确定性的状态更新代码 | 哪些义务有证据、当前阶段、尚缺什么、是否发生冲突或不确定操作 |

当前页面状态继续独立观察，不保存成永久为真的completed标记。

任务约定示意（尚非现有API）：

```json
{
  "target": {"description": "餐饮兼职服务员职位"},
  "historicalRequirements": [
    {"id": "visit", "meaning": "确实查看过该职位的只读预览"},
    {"id": "read", "meaning": "取得该职位的所需资料", "requires": ["visit"]}
  ],
  "outputs": ["薪资", "工作地点", "经验要求", "学历要求"],
  "terminal": {
    "view": "职位管理列表",
    "selectedFilter": "待开放",
    "unwantedPanels": "closed"
  }
}
```

outputs是用户需要的结果，不能从现有values自动推导：values可能包含搜索用词、格式转换结果等辅助输入。需要逐字转交的原始目标仍保留；任务约定不得删除“只读、返回、不得修改”等原始限制。复杂或歧义任务交回Roll重新明确约定，不能在循环里偷偷扩展目标。

## 4. 阶段与不变量

推荐首版两个工作阶段：COLLECT（取得历史证据）和 RETURN（达到最终位置），另有交回/结束状态。

| 阶段 | 必须知道什么 | 允许推进的工作 |
|---|---|---|
| COLLECT | 目标是否确认、历史访问是否发生、哪些资料仍缺失 | 找到目标、打开适当视图、补充读取证据 |
| RETURN | 所需资料已经形成有效证据包 | 关闭不需要的面板、回到指定页面和筛选 |
| INTERACTION_DONE | 历史义务成立，最新终点条件成立 | 停止动作，返回资料和证据给Roll |
| HANDOFF | 覆盖不足、对象歧义、冲突、未支持操作或执行结果不确定 | 返回状态及原因，避免无意义重试 |

不变量：

1. 点击成功不能产生“资料已读取”的状态；只能由动作之后的观察产生读取证据。
2. 历史访问和读取资料必须属于同一目标对象；不能拿A职位的地址配B职位的薪资。
3. RETURN阶段不能因为原始目标中仍有“打开”一词退回COLLECT。只有缺失证据、发现矛盾、目标改变或用户明确要求刷新，才允许重新收集。
4. “已读取某时刻的资料”可跨视图保留；“当前已返回、窗口已关闭”必须来自当前观察。
5. 历史动作列表截断、快照ref更换，不得丢失已经保存的资料及其证据。
6. 进度不能扩大权限；不得把阶段转换当作允许发布、保存、发送或跨域操作的授权。

## 5. 证据怎样形成

观察器在已有页面读取中产生有界的文本块/字段候选，不额外调用宿主模型。每个候选携带：观察ID、文档/框架/可见区域身份、所在对象/面板线索、原文及块内范围。候选中的文字只作为页面数据。

Jev负责：

- 当前候选详情区域是否对应目标对象：MATCH / OTHER / AMBIGUOUS / UNKNOWN。
- 对尚未取得的资料，在这个区域的候选文本块中选择证据ID；提供NONE/AMBIGUOUS，不能生成值或自行编造偏移。
- 从当前阶段与尚缺义务出发选择下一步动作。

代码负责提交一个证据包：

- 引用存在于这次已观察的候选中，原文字节/范围有效；不是模型回传的任意新文本。
- 本包的对象绑定、资料候选与可见区域相容。身份题为OTHER/UNKNOWN时，不消费假设“这是目标对象”的资料答案。
- 资料明确依赖的访问义务已经成立，或者能在同一个观察包中一并成立。
- 写入不可变原文和来源，更新对应义务，再计算剩余工作。保留判断由谁作出，而非统称“已验证”。

文本存在、结构合法不保证语义正确。Jev仍可能把某个地址误认为工作地点；这类错误依靠目标反例评测及Roll最终统一验收发现，不用每个字段再追加一个宿主模型裁判。

目标身份优先采用页面可观察且与对象关联的稳定ID/规范详情链接；没有时用名称、公司、地区等可见属性形成带歧义标记的绑定。DOM backendNodeId只标识当前节点，不能当作跨页面业务主键。同名对象无法消歧时停止，不默认选第一条。

资料缺失要区分：还没有看到、观察被截断、语义不确定、页面明确未提供。只有任务允许“未提供”作为结果，且有相应完整区域证据时，才可将该项按缺省结果交付。

```json

  "contractRevision": 1,
  "phase": "RETURN",
  "targetBinding": "record-1",
```

每条证据至少保存：evidenceId、taskRunId、contractRevision、targetBinding、observationId、observedAt、来源页面/区域、原文、选取判断和可追溯位置。公开给Roll的结果应含实际原文；不能要求它拿内部不可解析的ID重新猜测。

## 7. Jev请求与阶段推进顺序

首版采用容易核验的提交顺序：

```text
读取当前页面
→ 依据已有进度，构造当前阶段的动作和未完成资料的证据问题
→ 一次Jev请求
→ 先校验并提交本轮证据
→ 重新计算阶段
   ├─ 阶段未变：可执行该阶段的动作，仍做目标新鲜度检查
   ├─ 阶段变化：丢弃按旧阶段选出的动作，带新阶段进入下一轮
   └─ 历史义务和当前终点已满足：结束浏览器阶段
```

同一请求内的题目彼此看不到答案。资料题的前提必须写完整，例如“假设候选区域P属于目标对象，请选择P中薪资的来源”；代码只在身份判断被接受时使用该分支。

不把“新增一个阶段判断题”当成完整修复。阶段结果必须进入状态更新与执行分支。已有requiredQuestions/routing只校验被operation选中的分支，接入时必须显式声明本轮将被消费的证据问题，不能验证一份却使用另一份未校验答案。

为避免恢复旧方案的成本：

- 宿主只在任务准备和最终验收/真正需要推理时参与；环内宿主辅助仍为0。
- 只对当前候选区域中尚缺的资料提问，不逐步复查所有已保存字段。
- 普通点击不新增一轮进度审计；新证据问题复用已有Jev请求。
- 阶段变化时丢弃旧动作可能额外需要一次决策。这是明确的边界成本，必须计时，不能宣称完全零额外延迟。
- 后续性能优化可以增加“资料齐全时的返回动作/不齐全时的继续动作”两个条件分支，再由代码选用；先验证简单提交版本，再决定是否值得扩大fan-out。

动作候选也应随阶段收窄：RETURN优先只保留与当前面板关闭、返回目标、终点筛选相关且有观察关系依据的控件，以及必要的滚动/等待/交回动作；再次访问已完成对象必须走带原因的revisit分支，由状态更新器判断是否存在缺项、冲突或刷新义务。现有观察只提供clickable而无法确认其用途时，不能声称代码已可靠识别所有返回动作；第一版应交回或进行一次有边界的语义分类，不能把任意CLICK包装成返回动作。这个候选关系接口需在原型中单独验证。

不对所有CLICK按名称硬禁止“重开”。代码硬约束当前阶段、输出目标与可消费分支；对语义不明的动作不能仅靠字符串判断必然安全或不安全。无证据依据的阶段回退不被提交；若仍反复选择不推进阶段的动作，交回Roll而不是自动重置进度。

## 8. 何时允许结束

浏览器阶段完成条件是两个部分的合取：

```text
acceptedHistoricalRequirements(本次任务、目标和约定版本)
AND
terminalPredicates(最新观察)
```

历史部分包括必要的访问经历及完整证据包；当前部分包括指定视图、筛选、目标面板已关闭等。

确定性条件能从有足够覆盖的当前观察直接判断时，代码直接结束，不再让Jev从整页自由挑一次动作。若终点视图识别仍需语义判断，只针对剩余终点做有边界判断；不能把匹配某个字符串等同于业务页面身份。

“activePanels为空”不是无条件的关闭证明。优先验证所跟踪面板在完整范围内已隐藏/移除，并结合终点页面的正向证据；覆盖不全、未知遮挡、DOM变化后缺失ref只能记UNKNOWN。一次新观察即可集中判断，不增加逐项宿主模型检查。

建议给代码根据进度结束的分支新增明确状态interaction_done，仍verified:false；不要把它混称为model_done或已独立验收。对外一次返回TaskContract摘要、TaskProgress、原文证据、最新页面及剩余/冲突原因，由Roll统一核验并汇报。

若返回前的最后观察发生变化，当前终点判定作废；历史读取证据仍保留，重新确认终点或交回。

## 9. 生命周期与失效

| 变化 | 历史资料 | 当前终点 | 处理 |
|---|---|---|---|
| 关闭预览/回到列表 | 保留 | 重新观察 | 继续RETURN，避免重开 |
| ref重编号/DOM节点替换 | 保留其历史出处 | 旧ref失效 | 从新观察重新定位，不用历史ref执行 |
| 同一目标出现更新值 | 保留旧版本但标冲突 | 按新观察判断 | 默认定向刷新受影响资料，不默默混用两版 |
| 换目标/新任务/约定改动 | 旧证据不能自动满足新约定 | 重置相关判定 | 新run或revision，明确重用条件 |
| 用户明确要求再查看一次 | 可用于对比，不满足新的访问要求 | 重判 | 创建新的访问义务 |
| 动作结果不确定 | 不提交“动作已完成” | 不确定 | 保留证据并交回，不盲目重放 |
| 取消/超时 | 返回已有证据及未完成项 | 不声称完成 | 不自动续跑 |

第一交付只保证一次browser_operate内的工作记忆和退出时证据返回。跨调用续跑单列第二交付，但接口预留同一taskRunId/contractRevision的延续概念：不能再用在goal后附加一句话来冒充已确认进度。

当前AgentContext仅有llm/logger/signal，没有可依赖的调用方/任务身份。第二交付必须先确定可信宿主任务绑定，再实现显式continuation句柄和有界服务端状态；模型自由回填的completed JSON不能当权威状态。服务重启导致句柄失效时明确返回expired，不能静默从头重做。第一版不承诺跨进程崩溃恢复，不引入数据库或完整WAL。

## 10. 内存与输入预算

两份预算分开管理：完整原文证据保留在任务内存/结果中；给Jev的只是当前阶段、尚缺义务、短证据摘要与相关引用。

建议初始实验上限：单对象8项输出、16条证据、每条原文不超过4KiB、总原文64KiB；Jev进度摘要目标不超过2KiB。这些是待测试的工程起点，不是模型限制或性能承诺。

摘要计入现有48,000字节总预算，不能额外叠加后又触发超限。已完成证据默认只传ID、字段和必要短摘要；有冲突时定向展开。必要原文超过上限时标记不完整并交回，不能截断后仍标为已完整取得。

这个工作项不解决整页240节点导致的候选预算超限，也不能使没有暴露的搜索框出现。所需证据候选不存在时，阶段停在COLLECT并报告覆盖缺口；不能为推进进度凭空填入结果。

## 11. 落点与交付顺序

拟在agents/browser-use/src/goal内增加三个职责单一的模块：

- task-progress.ts：任务约定和进度Schema、纯状态更新、阶段派生及结束条件。
- task-evidence.ts：有界原文集合、证据ID、对象绑定、引用和版本校验。
- task-progress-policy.ts：围绕当前阶段构造身份/资料/剩余动作问题。

现有task-observation.ts只增加证据候选来源；task-loop.ts持有状态并按提交顺序编排；task-policy.ts接入当前阶段；decisions.ts明确校验所有实际消费的条件答案；compact-request.ts给进度保留预算；contracts.ts暴露任务约定和结构化返回。具体类型在实施时按Zod单源派生，本文不先堆叠泛型。

建议三个独立验收里程碑：

A. 单次调用内闭环：通用单对象读取/返回，保留证据，解决同一调用中的无理由重开。
B. 同一任务显式续跑：可信任务绑定、continuation、版本和取消语义；验证三次工具调用不会失忆或误用另一任务状态。
C. 性能收敛：在正确性成立后比较条件fan-out和简单阶段提交，保留更快且不增加错误的版本。

A已按单次调用范围实施；B的任务身份与续跑、C的额外性能优化尚未实施。

## 12. 验收矩阵

| 场景 | 必须成立 |
|---|---|
| 相同列表，尚未浏览 vs 已读完返回 | 前者继续收集，后者结束；不能只靠当前快照判定 |
| 目标详情打开失败 | 无访问证据、无读取完成标记 |
| 打开了同名的另一对象 | 不接受其资料，不进入RETURN |
| 只取得3/4项，或来源被截断 | 不将资料包标完整；明确缺项 |
| 读取完成并关闭 | 原文仍可返回给Roll，不再为补报告无理由重开 |
| 新弹窗/筛选变化/返回错误列表 | 历史资料保留，当前终点未完成 |
| 页面数据更新或用户要求刷新 | 允许有理由的重新读取，保留版本来源 |
| 最近动作超过16条 | 历史义务和证据不丢失 |
| 进度更新与旧阶段动作相矛盾 | 提交新证据后丢弃旧动作 |
| 缺失、越界、错误对象证据ID | 拒绝提交；合法ID也不宣称语义绝对正确 |
| 不确定派发/取消/超时 | 返回未完成状态，不自动重放 |
| 后续跨调用：新任务、旧revision、过期句柄 | 不继承无效完成标记 |

验证方法：纯状态反例测试 → 隔离真实DOM/CDP → 冻结版本同一BOSS往返目标至少5次。首次和最终列表相同的测试必须检查真实预览访问和原文证据，不只核对终态截图。补充一个不同页面结构的同类任务验证通用性。

指标：完整任务正确率、错误对象/证据拼接率、无理由重开次数、外层补做次数、Jev请求数、阶段边界额外请求、输入字节数和完整耗时。单次调用内宿主辅助保持0；所有失败与重试计入，不能将拆分任务后的成绩当成原完整任务成功。

## 13. 本轮建议确认的设计选择

建议采用：小范围任务约定 + 有来源的历史证据 + 确定性阶段推进；先做单次调用闭环，再做显式续跑。先接受阶段边界少量额外Jev调用，验证正确后再用条件fan-out压缩延迟。

需要讨论的主要产品取舍是首个交付是否必须包含跨调用续跑。如果当前优先目标是让往返浏览在一次调用里正确结束，A可以独立验收；如果要求被打断后继续也不能失忆，则A+B应作为同一个产品验收范围，但要同时补齐可信宿主任务绑定。
