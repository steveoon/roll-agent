Roll Remote Architecture · Protocol / Companion / Runtime

一句话，跨过公网，
指挥你家里的 Agent

远端 Web App 或桌面 App 里的一次聊天输入，是如何穿过 Relay、被本机 Companion 验关、经 stdio 递进 Runtime、唤起 LLM 调用工具，再把审批卡片与事件流送回你眼前的。本文按真实源码逐层拆解这条链路。

贯穿全文的案例 · 一次带审批的远程聊天
你在公司，用浏览器打开一个接入了 Roll 的招聘工作台，输入：「帮我回复 BOSS 直聘里所有未读候选人」。这句话要跨过公网，抵达你家里那台跑着 roll 的电脑，唤起 LLM、调用招聘 Agent 的发送工具——而「发送消息」是写操作，还得把审批卡片逆流递回你眼前，等你亲手点批准。
层级 4 层 协议 Runtime 1.3 · Relay Wire 1.1 · Control 1.0 对外事件 14 种 审批时限 ≤ 5 分钟

一句话从左走到右：请求顺流而下；审批卡片与事件流逆流而上。中间每一跳换一种协议。

01/ 10 · 全景
docs/adr/0001-remote-web-companion-boundary.md

四层拓扑：前台、总机、管家、车间

把整条链路想成一家上门服务公司：Web App 是前台（接待你），Cloud Relay 是云端总机（只转接、不进屋），Companion 是你家的管家（唯一有钥匙的人），Runtime 是车间（真正干活）。三份契约分别管三段线路：浏览器↔Relay 走 Relay Wire 1.1（首帧握手是 Browser Control 1.0），Relay↔Companion 走同一 Wire 协议但方向反过来——Companion 只主动出站拨号，从不监听端口；Companion↔Runtime 走 Runtime Protocol 1.3。

P0 固定拓扑：一个官方 Relay profile、一个设备、一个 Workspace、一个 controller（ADR 0001）。

packages/protocol

Runtime Protocol 契约：Zod schema、版本注册表（1.0→1.3）、事件与方法定义。纯类型与常量，无 IO。

packages/runtime

引擎本体：RuntimeServer、RuntimeService、ConversationEngine、AgentSession、tool-bridge、policy、SQLite ThreadStore。

packages/companion

管家基础库：CompanionWorkspace、RelayBridgeV11、InteractionBroker、LeaseManager、两套重放缓冲。

packages/relay-protocol

Relay 线协议：10 种帧、方法注册表、Control 1.0 握手、conformance 一致性套件（给独立 Relay 仓库对拍用）。

packages/relay-client

浏览器 SDK：原生 WebSocket、零 Node 依赖（有专门的打包守卫测试）、指数退避重连、序号收敛。Web App 用它。

packages/client-node

本机 SDK：spawn Runtime 子进程 + stdio JSON-RPC。Companion 和桌面 App（Electron 参考实现）都用它。

i
钥匙只在管家手里。云端 Relay 永远拿不到你本机的执行权——它只做转接；一切落到本机的动作都要经过 Companion 的白名单与验证（第 08 章）。
02/ 10 · 车间入口
roll runtime serve --stdio → runServer()

门缝下塞纸条：stdio 上的 NDJSON JSON-RPC

Runtime 是一个普通子进程，不开端口、不装网络栈——客户端和它说话的方式，是往 stdin 一行塞一条 JSON-RPC 2.0 帧（NDJSON），它从 stdout 一行一行回。像从门缝下塞纸条：一张纸条一件事，写完塞进去，回条从门缝滑出来。进门后请求经过三层：RuntimeServer（收发与分流）→ RuntimeProtocolAdapter（wire 编解码与版本投影）→ RuntimeService（Thread/Turn/审批的权威状态机）。

Client → Runtime 的 15 个方法（Runtime Protocol 1.3）

initializeclient.capabilities.set thread.listthread.createthread.open thread.snapshotthread.renamethread.delete thread.detachthread.capabilities turn.startturn.cancel runtime.events.resume（仅 1.3）operation.get approval.respond（仅 1.0 可写）

发一句话 = turn.start，参数 {requestId, threadId, turnId, input:{text}}——turnId 由客户端生成，requestId 用于幂等：同 ID 重发返回缓存结果，同 ID 不同参数直接报错（SHA-256 参数指纹）。反向还有两个 Server Request：approval.request 与 userInput.request（Runtime 反过来向客户端发起 JSON-RPC 请求，第 06/08 章）。

!
一个真实的张力点：stdio 帧上限是 4 MiB（STDIO_MAX_FRAME_BYTES），而协议 1.3 声明 Client 须能接收 17 MiB 帧、单条持久事件上限 16 MiB——CLI 组装点未覆盖 maxFrameBytes。超大事件在 stdio 传输上会先撞 4 MiB 这道墙。
03/ 10 · Agent Loop
AgentSession.runTurn() → streamText (AI SDK)

车间黑话与门口的翻译官

真正的推理循环在 AgentSession：把系统提示词、历史消息、整面工具墙交给 AI SDK 的 streamText()，停机条件是 stepCountIs(80) 或用户拒绝。LLM 像车间里的老师傅，边干边喊话——内部事件足足 18 种（SessionEvent）。但站在车间门口的翻译官 projectSessionEvent() 只把它们翻成 14 种对外通报（runtime.event）：6 种纯内部的黑话（debug、step-finish、compaction-* 等）直接不翻；user-input-required 则换了条通道——不走事件流，改走反向 Server Request。

streamText 的关键参数：tools（第 05 章的工具墙）、stopWhen:[stepCountIs(80), stopOnUserRejected()]、toolApproval 钩子（工具进闸门的第一跳）。

i
思考过程默认不出门。reasoning.summary.delta 只有宿主注入 reasoningSummaryProjector 时才会产生；否则 Runtime 连 reasoning-summary 这个 feature 都不对外声明。
04/ 10 · 记忆
RuntimeService.emit() → ThreadStore（node:sqlite）

会议纪要与白板：哪些事件值得记进档案柜

14 种对外事件在协议 1.3 里被分成两类。白板事件（ephemeral，5 种）是现场感：逐字打出的 message.delta、滚动的 tool.output——擦了就没，断线不补。纪要事件（durable，9 种）是事实结论：turn.started、message.completed、tool.completed、approval.*、turn.* 终态——先写进 SQLite 档案柜、拿到 eventId 和游标，才对外广播。断线重连后凭游标向档案柜要回放（第 09/10 章），UI 永远能收敛到正确终态，最多丢一点「现场感」。

Ephemeral · 白板 · 5 种

擦了就没，不承诺重放

message.started · message.delta · reasoning.summary.delta · tool.started · tool.output

只在连接活着时流过去。replay 期间到达的 ephemeral 会被旁路或丢弃——它们的使命是「让界面活着」，不是「构成事实」。

Durable · 纪要 · 9 种

先落库，再广播

turn.started · message.completed · tool.completed · approval.required · approval.resolved · turn.completed · turn.cancelled · turn.failed · capabilities.changed

事务内写入 runtime_events 表拿到 eventId + cursor（格式 rte1:日志:序号:事件）后才构造 envelope 发出。落库失败按致命错误处理：取消所有活动 Turn。

存在哪

~/.roll-agent/threads/threads.db，Node 内置 node:sqlite。目录 0700、DB 文件 0600、secure_delete=ON。

保留多少

每 Thread 最多 10,000 条 / 16 MiB / 30 天，只裁最老的连续前缀。裁掉的区间再来要回放，就报 EVENT_CURSOR_EXPIRED，逼客户端走快照收敛。

还存什么

消息正文（AI SDK ModelMessage）、工具执行记录（同样 30 天保留）、transcript、压缩检查点——Thread 的完整可恢复状态。

!
契约先于实现的一角：capabilities.changed 在协议里定义为 durable 事件，但当前 packages/runtime/src 里没有任何代码会发出它——它暂时只活在契约里。
05/ 10 · 工具墙
tool-bridge/build-tools.ts + ToolExecutionCoordinator

工具墙上挂着七类家伙，取用前先过秤

LLM 面前的「工具墙」在 AgentSession 构造时一次性拼好，七类来源统一命名为 agent__tool 或 roll__xxx。真正取用时走两阶段调度：同一批工具调用先串行过秤（参数 preflight → 策略闸门 → 资源计划），全体过秤后才并发执行，并发只受资源读写锁约束——两个工具要写同一个文件？排队。同批里有人被用户拒绝？其余全部取消。

agent__tool

MCP 子 Agent 的工具（如 zhipin__send_message），经 McpClientManager.callTool() 调用，是本案例的主角。

roll__bash / powershell

内建 shell。命令先过分类器；没有策略时无条件请求审批（fail-closed）。

roll__skill

只读加载 SKILL.md 正文与 references，不经确认门。

roll__user_input

让 LLM 反过来问用户要输入。动态注入：客户端声明支持 userInput.request 才出现在墙上。

roll__transcript

回读会话历史记录。

roll__agent_install + session exec

安装新 Agent；长驻 shell 会话（command/poll/list 三件套）。

i
先全体过秤、再一起动手——这保证「用户看到并批准的那一批」就是「实际执行的那一批」，不会批到一半又冒出新工具。
06/ 10 · 审批闸门
DefaultToolPolicy.check() → gateToolCall()

动焊枪前，先把工单递到你面前

案例里 LLM 要调用 zhipin__send_message。策略引擎看一眼工具名就拦下了：「send」是写动词。判定顺序只有四步：① 标了 destructiveHint → 必须确认；② 工具名分词后命中 30 个写动词之一 → 必须确认；③ 标了只读或命中 22 个读动词 → 放行；④ 都不认识 → 默认必须确认（fail-closed：不认识的东西一律当危险品）。「确认」意味着 gateToolCall() 在这里 await 一张审批工单的回执——批了才执行，拒了返回 user_rejected。

交互沙盘 · 策略判定器（逻辑与 default-policy.ts 逐字一致）
confirm——

工具名按 /[_\-\s]+/ 分词。红色 token 命中写动词表，绿色命中读动词表。注意规则顺序：写动词检查在只读标注之前——名字里带 send 的工具就算标了 readOnlyHint 也要确认。

工单的寿命 ≤ 5 分钟

审批截止时刻 = min(now + 5min, 本 Turn 的超时时刻)。到期、Turn 取消、连接断开——任何一种情况，ApprovalGate.abortAll() 都把未决工单统一结算为 approved: false。不存在自动批准的路径；默认值永远是拒绝。

想改默认位？

ConfigurableToolPolicy 提供三档默认（guarded / auto / deny）+ 按 agent.tool 的逐工具覆盖（auto/confirm/deny）。deny 会让 gateToolCall 直接返回 policy_denied，连工单都不发。

!
客户端没接住工单会怎样？审批请求过期或投递失败时，Runtime 不会「视为同意」，而是记下失败原因并取消整个 Turn——终态是 turn.failed。宁可这轮白干，不替用户做主。
07/ 10 · 管家
roll companion run --foreground → DefaultCompanionSessionFactory

管家的一天：拉起车间、接听总机、挂好登记牌

Companion 是常驻你本机的守护进程（macOS LaunchAgent / Windows 计划任务）。它启动时做一串固定动作：先造好 InteractionBroker（审批工单的收发室），再用 client-node spawn 出 Runtime 子进程（roll runtime serve --stdio）并断言协议必须是 1.3，然后套上 CompanionWorkspace（聚合根），接上 RelayBridgeV11，最后向 wss://{host}/v1/companion 出站拨号。Runtime 崩了？监工 Supervisor 整体重启，退避 500ms 起步、翻倍到 30s 封顶，稳定运行 30s 后归零。

Lease：门口的登记牌，不是锁

四种登记牌：client / turn / shell-session / approval。开一个 Turn 挂一块，收到终态事件摘掉；有审批在途也挂一块。它的唯一用途是 canStopRuntime()——牌子全摘光才允许熄灯关车间。没有超时、没有抢占、没有互斥语义。

顺带澄清：roll ui 不是聊天界面

roll ui 启动的是本机配置台（React SPA，仅监听 127.0.0.1）：编辑 YAML、管理 Agent、以及一个 Companion 管理面板（enroll/启停/doctor/日志）。近期 commit「inject the companion controller」注入的正是这个管理面板的控制器——不是把 Companion 跑起来，更不是聊天窗口。

i
为什么 localApprovalPolicy 是无条件 allow？源码注释写得直白：「Runtime policy is the sole approval fact source」——审批的事实源只有一个（第 06 章的 Runtime 策略），管家不做第二次人为把关，避免两套策略互相打架。
08/ 10 · 海关
projectRuntimeEventEnvelopeForRelayV11 · InteractionBroker.submitCandidate

出关要申报，进关要过五道门

Companion 站在信任边界上，两个方向各设一套关卡。出关（本机 → 公网）是最小申报：tool.output 整个被扣下不出关；审批工单出关时只剩四个字段——approvalId、agentName、toolName、explanation（≤100 字）；工具的输入输出、preview 在类型层就不可表达，想带都带不出去。进关（公网 → 本机）是五道门，任何一道不过就拒绝，全部 fail-closed。

{accepted:true} 只表示候选被受理，不代表工具已执行；浏览器要等有序到达的 interaction.resolved 与后续 tool.completed 才能收敛视图。

进关五道门（fail-closed）

① Wire schema 校验 → ② 连接级 requestPolicy（P0 白名单，见右）→ ③ responderPolicy（要求已认证传输 + 官方 Relay profile）→ ④ Broker 身份三元组：interactionId + threadId + turnId + method 必须与在途工单完全一致 → ⑤ 本地审批策略。任何一道抛错都按拒绝处理。

P0 远程方法白名单 · 仅 9 个

thread.listthread.createthread.open thread.snapshotthread.capabilities turn.startturn.cancel operation.getinteraction.candidate

注意不含 thread.rename / delete / detach——云端连改名删除会话都不行。白名单之外统一回 REMOTE_REQUEST_DENIED。

!
唯一允许的插队：拒绝可以抢占进行中的批准。同一工单同时只允许一个在途候选，但一个单独授权的 reject 可以打断正在跑的 approve——插队只允许朝「收窄权限」的方向发生。
09/ 10 · 挂号信
relaySequence · runtime.ack · CompanionRelayFrameBuffer

连号的挂号信：断了号就要求补拍全家福

公网这段用 10 种帧说话（device.connect、runtime.request/response/event/ack/gap/encrypted + 三种 interaction.*）。所有发往浏览器的帧共享一个单调递增的 relaySequence，像连号的挂号信；浏览器只按 last+1 连号签收，每签一封回一张 runtime.ack 回执。Companion 手里留着一个重放缓冲（10,000 帧 / 32 MiB，塞满丢最旧）；重连后从对方确认过的号码续投。要是缺的号已被挤出缓冲？发一帧 runtime.gap，让浏览器别等了——直接 thread.snapshot 拍张全家福收敛。

Companion ↔ Relay 断线

每次连接是一个 generation：旧代作废时在途候选全部 abort，迟到结果不会串到新连接。重连成功后从 acknowledged + 1 重投缓冲帧；Relay 的 ACK 不允许超过本代已成功发送的最高序号。出站重连退避 500ms→30s。

浏览器 ↔ Relay 断线

relay-client 指数退避重连（250ms 翻倍、30s 封顶）；session 级错误不可重试则永久关闭。gap 恢复动作是「刷新所有已打开 Thread 的快照」而非重放——用 streamEpoch 防止旧纪元的恢复结果污染新连接。

i
为什么用快照而不是重放收敛？Relay 帧缓冲是进程内的、会丢最旧的；而 durable 事件的权威档案在 Runtime 的 SQLite 里。跨了两跳之后，最可靠的收敛方式不是「补发我丢的信」，而是「重新拍一张现状全家福」。

一句话，记住整条链路

          
浏览器一句话 → Relay 总机转接 → 管家验关（白名单 + 五道门） → stdio 纸条递进车间 → LLM 取工具、策略拦下写操作 → 审批卡片逆流到你眼前 → 你点批准 → 工具执行 → 事件挂号信顺流而下、连号签收。

          
四层各司其职：protocol 定契约（说什么），runtime 干活并记账（做什么、记什么），companion 守边界（谁能进、什么能出），relay/app 管转接与呈现。安全底色只有一句：默认拒绝，最小申报，钥匙永远不出你家门。
