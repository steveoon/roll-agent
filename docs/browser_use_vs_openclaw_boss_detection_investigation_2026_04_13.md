# browser-use-agent vs OpenClaw 浏览器链路差异调查报告（Boss 直聘反自动化）

日期：2026-04-13  
作者：来财

---

## 1. 背景

用户反馈：

- 使用 `browser-use-agent` 通过 CDP 连接并打开的 Chrome 浏览器访问 **Boss 直聘** 时，点击登录后会**立即自动跳转回 `about:blank`** 或回首页。
- 该问题重复多次后，会触发 Boss 直聘的**封号/风控机制**。
- 但当改用 **OpenClaw 自己的浏览器链路**（也是 CDP 相关的新浏览器实例，并安装了 OpenClaw Browser Relay 扩展）访问 Boss 直聘时：
  - 进入登录页正常
  - 不会自动跳回 `about:blank`
  - 登录流程可正常进行
- 同时，`browser-use-agent` 打开的浏览器访问**非 Boss 网站**时没有这个问题。

初步判断：

- 问题大概率不是“Chrome 无法工作”或“CDP 本身不可用”
- 而是 **Boss 直聘的反自动化 / 反调试 / 风控机制** 对 `browser-use-agent` 这条浏览器链路更敏感
- OpenClaw 的浏览器控制方式似乎规避了该侦测

---

## 2. 本次调查目标

本次调查主要是对比：

1. `browser-use-agent` 的浏览器启动 / CDP 连接 / 打开页面方式
2. OpenClaw 自己浏览器链路的启动 / CDP 连接 / 打开页面方式
3. 两边浏览器 profile、扩展、启动参数、控制方式的差异
4. 推测哪一层更可能触发 Boss 直聘的反自动化侦测

---

## 3. 调查方法

本次调查使用了以下方式：

- 拉取并更新本地 `roll-agent` 源码
- 对比本地 `openclaw` 源码中的浏览器实现
- 反查已安装的 `browser-use-agent` 运行时代码（dist 产物）
- 检查两边浏览器 profile 的落盘目录、Local State、Preferences、Extensions
- 读取扩展 manifest 与注入脚本
- 验证用户额外提供的实验结果：
  - 卸载 `Anti Anti Debug` 插件后，**Boss 反自动化仍然触发**

## 4. 关键事实与发现

### 4.1 `browser-use-agent` 底层是 Playwright `connectOverCDP`

从已安装产物 `@roll-agent/browser/dist/index.js` 可见，`browser-use-agent` 的 `managed-cdp` 模式核心逻辑是：

1. 本地启动 Chrome/Chromium/Edge
2. 指定 `--remote-debugging-port`
3. 指定 `--user-data-dir`
4. 然后立即执行：

```ts
chromium.connectOverCDP(cdpUrl)
```

也就是说：

- **浏览器一启动，就被 Playwright 通过 CDP attach**
- 整个浏览器会话从一开始就处在自动化框架控制之下

对应的运行时默认值包括：

- `mode = managed-cdp`
- `headless = false`
- `cdpPort = 9222`
- `channel = chrome`
- 默认 userDataDir：
  - `~/.roll-agent/browser/profiles/managed-default`

### 4.2 `browser-use-agent` 的 Chrome 启动参数

从运行时代码中可见，`browser-use-agent` 在 `managed-cdp` 下会以大致如下参数启动 Chrome：

- `--remote-debugging-port=<port>`
- `--user-data-dir=<dir>`
- `--no-first-run`
- `--no-default-browser-check`
- `--disable-background-networking`
- `--disable-component-update`
- `--disable-session-crashed-bubble`
- `--hide-crash-restore-bubble`
- 如果 headless 则追加：
  - `--headless=new`
  - `--disable-gpu`
- 最后固定打开：
  - `about:blank`

然后 `open_platform` 再通过 Playwright page 对当前页执行：

```ts
page.goto("https://www.zhipin.com")
```

### 4.3 OpenClaw 的浏览器启动方式

OpenClaw 自己的浏览器链路同样会：

- 启 Chrome
- 开 `--remote-debugging-port`
- 指定 `--user-data-dir`
- 打开 `about:blank`

其 `chrome.ts` 中的关键启动参数大致为：

- `--remote-debugging-port=<profile.cdpPort>`
- `--user-data-dir=<userDataDir>`
- `--no-first-run`
- `--no-default-browser-check`
- `--disable-sync`
- `--disable-background-networking`
- `--disable-component-update`
- `--disable-features=Translate,MediaRouter`
- `--disable-session-crashed-bubble`
- `--hide-crash-restore-bubble`
- `--password-store=basic`
- Linux 下可追加 `--disable-dev-shm-usage`
- headless 时追加 `--headless=new --disable-gpu`
- 末尾也会追加：
  - `about:blank`

### 4.4 OpenClaw 打开页面时并不总是先走 Playwright `page.goto`

这是本次调查中非常关键的一点。

OpenClaw 在打开新标签页/导航时，优先尝试使用原生 CDP：

```ts
Target.createTarget({ url })
```

也就是说：

- 它很多时候是**通过 CDP 原生命令直接创建目标 tab**
- 而不是像 `browser-use-agent` 那样先拿到 Playwright page 再 `page.goto()`

只有在某些特定条件下，OpenClaw 才会走 Playwright-backed 的 create page 流程。

### 4.5 OpenClaw 的 Playwright attach 节奏更“按需”

OpenClaw 的 `pw-session.ts` 也使用：

```ts
chromium.connectOverCDP(endpoint)
```

但结合 `browser open` / `Target.createTarget` 链路来看，它的浏览器控制模型更像：

- 浏览器先以更原生的 CDP 方式起标签页
- 再根据后续具体操作，按需建立 Playwright 连接/会话

而不是像 `browser-use-agent` 那样：

- **浏览器刚启动就整体挂在 Playwright 自动化框架下面**

这意味着：

- 两者虽然都“使用 CDP”
- 但**被 Boss 感知到的自动化痕迹强度并不一样**

## 5. 浏览器 profile / 扩展差异

### 5.1 `browser-use-agent` profile

目录：

- `~/.roll-agent/browser/profiles/managed-default`

读取到的 profile 特征：

- profile 名称：`您的 Chrome`
- `shortcut_name = None`
- `profile_color_seed = -16033840`

### 5.2 OpenClaw profile

目录：

- `~/.openclaw/browser/openclaw/user-data`

读取到的 profile 特征：

- profile 名称：`openclaw`
- `shortcut_name = openclaw`
- `profile_color_seed = -47872`
- `browser.theme.user_color2 = -47872`
- `autogenerated.theme.color = -47872`

说明：

- OpenClaw 会对 profile 做**显式装饰与稳定化处理**
- 包括 profile 名称、颜色、Local State / Preferences 写入
- `browser-use-agent` 这边则更像通用 managed-default profile

### 5.3 扩展差异

#### OpenClaw 浏览器扩展

OpenClaw 浏览器 profile 中存在扩展：

- ID: `nglingapjinhecnfejdcpihlpneeadjp`
- 名称：`OpenClaw Browser Relay`

特点：

- 权限集中在：
  - `debugger`
  - `tabs`
  - `activeTab`
  - `storage`
- host permissions 仅限：
  - `http://127.0.0.1/*`
  - `http://localhost/*`
- **不是 `<all_urls>` 注入型扩展**
- 不会在每个站点 `document_start` 修改网页 JS 运行时

#### `browser-use-agent` managed profile 中的扩展

在 `browser-use-agent` 的 managed-default profile 中发现扩展：

- ID: `mnmnmcmdkigakhlfkcdimghndnmomfeo`
- 名称：`Anti Anti Debug`

特点：

- `content_scripts.matches = <all_urls>`
- `run_at = document_start`
- 会向所有页面最早阶段注入脚本

注入脚本 `anti-anti-debug.js` 会修改：

- `console.log`
- `console.table`
- `console.clear`
- `Function.prototype.constructor`
- `document.createElement`

并会尝试拦截带有 `debugger` 的代码。

## 6. 关于 `Anti Anti Debug` 的结论修正

本次调查初期，`Anti Anti Debug` 曾被认为是**第一嫌疑**。  
理由很简单：

- `<all_urls>`
- `document_start`
- 修改运行时原生对象
- 这类行为极容易碰到 Boss 直聘的前端风控 / 反调试检测

但是，用户后续补充了一个非常关键的实验结论：

> **卸载 `Anti Anti Debug` 插件后，Boss 直聘的反自动化检测依然触发。**

因此需要修正结论：

- `Anti Anti Debug` **不是唯一主因**
- 甚至**可能不是主因**
- 它至多属于“可能加重可疑度的因素”
- 但 Boss 的核心拦截点，更可能在别处

---

## 7. 当前最可能的根因判断

综合源码、profile、扩展、连接方式、以及用户提供的实验结果，目前最可能的根因排序如下：

### 7.1 第一嫌疑：`browser-use-agent` 的“持续 Playwright attach 整个浏览器”模式

`browser-use-agent` 的模式是：

- 启浏览器
- 开 CDP 口
- 立即 `chromium.connectOverCDP`
- 后续页面使用 Playwright page / context 管理

这意味着：

- 浏览器从一开始就处于被自动化框架完整接管的状态
- 对于 Boss 这种强风控站点，更可能命中“自动化浏览器环境”识别

而 OpenClaw 的打开标签方式中，优先使用：

- `Target.createTarget`

这更接近“原生 CDP 打开一个正常标签页”，
而不是“先把整个浏览器变成 Playwright 自动化对象再打开站点”。

**这是目前最值得重点怀疑的差异。**

### 7.2 第二嫌疑：`page.goto()` vs 原生 `Target.createTarget()` 的开页差异

`browser-use-agent.open_platform` 的开页逻辑更像：

- 拿到当前 Playwright page
- 对该页执行 `page.goto(zhipin)`

而 OpenClaw 的浏览器打开链路很多时候更像：

- 原生 CDP `Target.createTarget({ url })`

这可能导致的差异包括：

- 页面初始加载上下文不同
- 站点观察到的调试/自动化特征不同
- 登录页的跳转与安全策略表现不同

在 Boss 这种站点上，这种差异可能足以触发不同风控路径。

### 7.3 第三嫌疑：profile 与启动参数整体指纹差异

两边虽然都用到了：

- `--remote-debugging-port`
- `--user-data-dir`
- `about:blank`

但仍有差别：

- OpenClaw profile 做了明确装饰与清理
- OpenClaw 额外参数更多、更稳定（例如 `--disable-sync` / `--password-store=basic` / 主题色 / profile name）
- `browser-use-agent` 默认 profile 更“通用/野生”

单看这层不一定致命，
但它可能和“整体自动化接管方式”叠加，增加被识别概率。

### 7.4 第四嫌疑：`Anti Anti Debug` 扩展是放大器而非根因

现阶段更合理的表述应为：

- `Anti Anti Debug` 可能会让环境更可疑
- 但即使移除，Boss 依旧能识别 `browser-use-agent`
- 所以它更像**放大器**，不是核心根因

## 8. 为什么非 Boss 网站没事？

这与调查结果是吻合的。

解释如下：

- 普通网站对 DevTools / CDP / Playwright attach 不敏感
- 或没有专门的前端反自动化机制
- 所以 `browser-use-agent` 可以正常访问

而 Boss 直聘：

- 明显有更强的前端风控 / 登录保护 / 自动化侦测机制
- 会对异常浏览器环境做更激进的处理
- 包括：
  - 自动跳回 `about:blank`
  - 回首页
  - 重复后触发封号/风控

所以问题不是“browser-use-agent 无法浏览网页”，而是：

> **Boss 直聘这个站点，能识别并拦截 browser-use-agent 这一类浏览器控制环境。**

---

## 9. 当前结论（精简版）

### 可以确定的

1. `browser-use-agent` 和 OpenClaw **都使用 CDP**，所以问题不在“是否用了 CDP”本身。
2. `browser-use-agent` 的浏览器从启动开始就被 Playwright `connectOverCDP` 持续接管。
3. OpenClaw 打开页面时，很多场景优先走原生 CDP `Target.createTarget`，并非总是先走 Playwright `page.goto()`。
4. `browser-use-agent` 曾包含 `Anti Anti Debug` 扩展，但用户已验证：**即使卸载该扩展，Boss 反自动化仍然触发。**

### 最可能的解释

> **Boss 直聘并不是单纯检测“有没有 CDP”，而是在检测更完整的自动化接管特征。**

当前最像主因的是：

- `browser-use-agent` 的 **managed-cdp + 立即 connectOverCDP + Playwright page/goto** 整体链路
- 相比之下，OpenClaw 的浏览器链路更轻、更偏原生 CDP target 创建，更像普通用户浏览器行为

因此：

> **OpenClaw 真正规避侦测的关键，很可能不是某个单独插件，而是“浏览器控制方式本身更原生、更按需、更少暴露 Playwright 自动化特征”。**

## 10. 建议的下一步验证方案

为了真正钉死根因，建议 Claude Code / 后续调查继续按下面顺序做 A/B 测试：

### 方案 A：保留 browser-use-agent，但去掉“启动即 Playwright attach”

目标：

- 浏览器先仅以 CDP 口启动
- 不立即 `connectOverCDP`
- 打开 Boss 页时优先尝试原生 `Target.createTarget`

如果这样恢复正常，说明：

- **问题主要是 Playwright 持续 attach 整个浏览器**
- 而不是纯粹的 Chrome 启动参数问题

### 方案 B：保留 browser-use-agent 其他逻辑，只把打开页面方式从 `page.goto()` 改为原生 CDP `Target.createTarget()`

目标：

- 让 browser-use-agent 更接近 OpenClaw 的开 tab 方式

如果问题显著改善，则说明：

- **Boss 对“Playwright 风格 page navigation”更敏感**

### 方案 C：复刻 OpenClaw 的 user-data/profile 装饰与参数

包括：

- profile name
- theme color
- Local State / Preferences 修饰
- 启动参数与清理策略

如果问题改善，则说明：

- profile 指纹 / 启动参数也参与了风险累积

### 方案 D：比较登录页请求链路与 JS 运行差异

建议进一步抓：

- 登录按钮点击前后的 URL 变化
- 跳到 `about:blank` 前是否有脚本重定向
- Console / network / CSP / challenge 请求差异
- `navigator.webdriver`、DevTools/automation 相关探针结果

## 12. 最终一句话结论

> **现阶段最有力的判断是：Boss 直聘拦截的不是“CDP”本身，而是 `browser-use-agent` 这一整套“启动即 Playwright 接管浏览器 + page.goto 导航”的自动化控制方式；OpenClaw 的浏览器链路之所以更稳，是因为它更偏原生 CDP tab 创建、按需控制、暴露的自动化痕迹更弱。**
